# 3 系统需求分析

本章对基于 Agent 的课程助教系统的需求进行分析。首先概述系统的整体需求，随后围绕学生、教师、管理员三类角色开展功能需求分析，并从界面、安全、性能等方面分析非功能需求，最后从技术可行性与经济可行性两方面进行可行性分析。

## 3.1 需求概述

基于 Agent 的课程助教系统旨在利用大语言模型与多智能体技术，为高校计算机专业课程提供智能化的教学辅助服务，核心目标是实现课程答疑、作业批改、试题生成三大任务，并辅助教师掌握学情。

系统面向三类用户：

（1）学生用户。学生登录后，可基于课程知识库进行多轮智能答疑，系统以流式方式返回答案并附来源引用；学生还可查看历史会话记录。

（2）教师用户。教师登录后，可上传课程知识文档构建知识库，可查看学生的作业提交并对作业进行 AI 辅助批改（评分与生成评语），可依据知识点、数量与难度批量生成试题，并可查看课程的学情统计数据。

（3）管理员用户。管理员除拥有教师的相关权限外，还可查看与管理后台中的 Agent 配置信息以及系统运行日志。

系统的整体业务流程为：教师首先上传课程知识文档并构建课程知识库；学生在问答界面基于知识库提出课程相关问题，系统答疑 Agent 结合检索知识与大语言模型给出带溯源的流式回答；学生提交作业后，教师可调用批改 Agent 进行智能评分与评语生成；教师可调用出题 Agent 生成试题用于课后练习；同时，系统汇总答疑、批改、出题等数据进行学情统计。

## 3.2 需求分析

### 3.2.1 功能需求分析

根据系统需求，本系统主要划分为认证管理、智能答疑、知识库管理、作业批改、智能出题、学情看板六个功能模块。系统功能结构图如图 3.1 所示。

（1）认证管理模块。所有用户通过统一的登录页面使用用户名和密码进行登录，系统根据用户角色跳转到对应的功能界面。未注册用户可在注册页面创建学生账号。登录验证通过后，系统在客户端写入会话令牌，并据此进行后续的权限控制。

（2）智能答疑模块。学生用户可发起新的会话，输入课程相关问题，系统答疑 Agent 基于课程知识库进行检索增强生成，以流式方式逐段返回答案，并在回答末尾标注来源引用（如"数据结构讲义.docx·片段3"）。系统支持多轮会话，学生可查看历史会话与消息记录。

（3）知识库管理模块。教师与管理用户可查看所授课程已入库的知识文档列表，并可上传 .txt、.md、.pdf 等格式的课程文档。系统对上传文档进行切分、向量化并入库，作为答疑 Agent 的检索来源。各课程的知识库相互隔离。

（4）作业批改模块。教师可查看某课程学生的作业提交列表及其批改状态，对尚未批改的作业调用批改 Agent 进行 AI 辅助批改。批改 Agent 依据统一评分标准输出百分制得分与针对知识点的评语、错误指出及改进建议，批改结果存入数据库。

（5）智能出题模块。教师可依据课程、知识点、题目数量与难度批量生成试题。出题 Agent 生成覆盖选择、填空、简答等题型的结构化试题，并包含参考答案与难度等级，生成的试题存入题库并可在页面展示。

（6）学情看板模块。教师与管理员可查看某课程的学情统计数据，包括选课人数、作业提交数量、已批改数量、平均得分、知识文档数量、试题数量与答疑消息数量等，帮助教师了解教学与学习整体情况。

### 3.2.2 非功能需求分析

（1）界面需求。系统界面应简洁、清晰、操作便捷，不同角色登录后进入对应的功能界面，交互流程直观易用。对话界面应支持流式输出，减少等待感。

（2）安全性需求。系统应实现基于角色的访问控制，学生、教师、管理员权限相互隔离，未授权用户无法访问对应功能；用户口令以哈希形式存储；大模型 API 密钥通过环境变量配置，不进入代码仓库与系统界面。

（3）性能需求。系统应能对学生的提问及时响应，对话内容以流式方式实时返回；知识库检索应满足即时性需求；系统应支持多用户并发访问，核心功能运行稳定。

（4）可靠性需求。当大模型 API 不可用或调用出错时，系统应能够优雅降级（如返回友好错误提示），不应导致整个流程崩溃；知识库检索在无索引时应能够正常给出提示而非异常。

（5）可维护性需求。系统采用模块化分层结构，智能体、知识库、接口、前端页面相互分离，便于后期维护与功能扩展；配置项集中管理，便于在不同环境部署。

## 3.3 可行性分析

（1）技术可行性。本系统所选技术栈成熟且社区生态完善：大语言模型采用阿里云百炼提供的通义千问 API，具备稳定的云端调用能力；LangChain 与 LangGraph 提供了成熟的模型封装与多智能体编排能力；FAISS 提供了高效的向量检索；FastAPI 生态完善、开发效率高；MySQL 稳定可靠。以上技术均已有大量成熟应用，技术上完全可行。

（2）经济可行性。系统所需软件环境均为开源或免费软件（Python、FastAPI、MySQL、FAISS、LangChain/LangGraph）；大语言模型 API 采用按量计费，验证阶段用量有限、成本可控；系统部署在普通个人计算机即可完成开发与演示，无需额外购买高性能硬件。因此，系统开发的直接经济投入较小，经济上可行。

（3）操作可行性。系统面向教师、学生、管理员三类用户提供网页界面，操作方式符合日常使用习惯，无需用户具备专业技术背景；系统部署与配置过程已在实施阶段验证可行。因此，系统在操作层面可行。

## 3.4 本章小结

本章对系统进行了需求分析。通过需求概述明确了系统面向学生、教师、管理员三类用户的核心目标，围绕认证管理、智能答疑、知识库管理、作业批改、智能出题、学情看板等模块进行了功能需求分析，并从界面、安全、性能、可靠性、可维护性等方面分析了非功能需求，最后从技术、经济、操作三个层面论证了系统的可行性。
